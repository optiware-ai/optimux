Command approval

Off on servers (OPTIMUX_SERVER=1): every command needs your approval.

Sandbox

With the sandbox on, every command the model runs goes through bubblewrap (Linux):

  • only the working folder (the active project, or the Workspace folder) can be changed;
  • the rest of the system is read-only (tools and compilers still work);
  • your home folder and Optimux's own folder (keys, token, chats) are hidden; ~/.gitconfig and your global skills stay readable;
  • /tmp is private and empty, other processes are invisible, and the network can be cut.

If bubblewrap is missing or broken while the sandbox is on, commands are refused, never run unprotected.

On a server others can reach, start Optimux with OPTIMUX_SERVER=1 (or just OPTIMUX_REQUIRE_SANDBOX=1): the sandbox is then always on and can't be turned off here.

Extra read-only foldersOne absolute path per line, for things a project needs outside its folder (a shared virtualenv, another repository it imports). They are visible but can't be changed. Optimux's own folder and whole home folders are refused.

Command environment and limits

Commands get only a few basic variables (PATH, HOME, LANG, TERM…). Everything else in the server's environment, including every key and token, is left out.

List extra variable names a project needs (one per line). Keys Optimux keeps in secrets.env can't be added.

Limits apply to each command (0 = none). Memory caps address space, which some tools (Node, Go, Java) reserve generously, so leave it at 0 unless you need it. The process limit counts all processes of the server's user, so set it well above what Optimux itself runs. On a server, the systemd unit in deploy/ also limits Optimux as a whole.
